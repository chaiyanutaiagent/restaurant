## ขอบเขตระยะแรก

## สถานะล่าสุด — ข้อ 3 Document Lifecycle ขึ้น UAT แล้ว

วันที่ 13 ตุลาคม 2026: migration `doclife0030`, backend/frontend `uat-document-lifecycle-20261013`
ข้อความระยะแรกและ 3A/3B ด้านล่างเป็นประวัติการส่งมอบ ให้ใช้สถานะส่วนนี้เป็นปัจจุบัน

- เก็บหลักฐานใหม่ครบ 6 ประเภทในทะเบียนเดิม: PO เมื่ออนุมัติ, GR เมื่อรับสินค้า,
  ทะเบียนรับใบแจ้งหนี้ผู้จำหน่ายเมื่อบันทึก, ใบสำคัญจ่าย/WHT เมื่อจ่าย, ใบกำกับ/ใบลดหนี้เมื่อออก
- ผู้ขาย/ผู้ซื้อ/รายการ/ยอด/เลขเดิม/ผู้บันทึกหรืออนุมัติ/เวลา/แม่แบบและ HTML ถูกเก็บใน transaction เดียวกับต้นทาง
  รวม XML ที่มี ณ วันออกเอกสารภาษี; checksum ไม่ใช่ลายเซ็นดิจิทัล และไม่ได้เก็บ PDF byte-for-byte
- PO เก็บข้อมูลก่อนและหลังแก้ร่างพร้อมเหตุผล ผู้แก้ และลำดับรุ่น; อนุมัติแล้วแก้ทับไม่ได้
  หลังยกเลิกสามารถสร้างร่างทดแทนเลขใหม่ที่เชื่อมกับต้นฉบับได้ครั้งเดียว และต้องส่งอนุมัติใหม่
- ยกเลิก PO/ใบแจ้งหนี้เจ้าหนี้/เอกสารภาษีผ่าน workflow เดิม พร้อมเหตุผลและผู้ดำเนินการ
  ใบลดหนี้เชื่อมกับเอกสารเดิม รวม UAT non-fiscal refund ที่ระบบรองรับอยู่แล้ว
  ไม่เพิ่มปุ่มยกเลิกการจ่ายหรือ GR ที่ข้ามการกลับบัญชี/สต๊อก และไม่ให้แก้ยอดเงินจากทะเบียน
- Database ป้องกัน UPDATE/DELETE/TRUNCATE ทั้ง snapshot และเหตุการณ์; เหตุการณ์มีลำดับไม่ซ้ำต่อเอกสาร
- เลข PO/GR/เอกสารภาษีใช้ lock คงที่ข้าม worker และลำดับสูงสุดตามข้อกำหนด unique เดิมของฐานข้อมูล
  ไม่เปลี่ยนเลขเอกสารเก่าและไม่เปลี่ยนเป็นระบบเลขแยกสาขาที่อาจชน constraint เดิม
- หน้าศูนย์เอกสารกดเลขเพื่อดูประวัติ ผู้ดำเนินการ เหตุผลและข้อมูลรุ่นเดิมได้ แบ่งหน้า 25 เหตุการณ์
- ดาวน์โหลดต้นฉบับจากหลักฐานผ่านทะเบียนได้ครั้งแรกครั้งเดียว ที่เหลือเป็นสำเนา มีประวัติคำขอดาวน์โหลด
  หากเครือข่ายขาดหลังบันทึกการขอต้นฉบับ ให้ใช้สำเนา ไม่สร้างธุรกรรมใหม่
  สำเนาเอกสารที่ยกเลิกมีป้าย CANCELLED; ไม่ใช่การรับรองต้นฉบับทางกฎหมายหรือผลพิมพ์ที่เครื่องจริง
- เอกสารเก่าแสดงประวัติ audit เดิมแยกจากหลักฐานใหม่ ไม่ backfill ชื่อ/ที่อยู่ปัจจุบันเป็นข้อมูลอดีต
  ถ้าเอกสารใหม่ระบุว่ามีหลักฐานแต่หลักฐานหาย/ไม่ตรง checksum จะปฏิเสธ ไม่ fallback ไปข้อมูลปัจจุบัน
- ทะเบียนรับใบแจ้งหนี้ผู้จำหน่ายเป็นเอกสารภายใน ไม่ใช่ต้นฉบับใบแจ้งหนี้ที่ผู้จำหน่ายออกหรือระบบสแกนไฟล์แนบ
- คง routing เดิม: จัดซื้อใช้ operational context ส่วน AP/e-Tax ใช้ฐานเดิมตามบริการปัจจุบัน
  ไม่ย้าย Retail data source และไม่เพิ่มทะเบียน PO/GR ของ Takeaway ที่ใช้โมเดลคนละชุด

ผลตรวจ: unit 69 กรณีผ่านรวมการตรวจซ้ำเฉพาะกรณีที่แก้, browser 13 กรณีผ่านรวมกรณีแก้ fixture,
type-check/build ผ่าน; integration ในฐานสำเนา network-none ผ่านทั้ง 6 ชนิด/PDF,
PO และ original-export race, AP idempotency/overpayment, scope, immutable triggers,
revision/cancel/replacement/credit-note linkage และการ rollback GR หากเก็บหลักฐานไม่ได้
ไม่มีธุรกรรมทดสอบทางบัญชีเขียนบน UAT จริง; live smoke อ่านประวัติ 6 ประเภท, health 200, anonymous API 401

การเผยแพร่ครั้งแรก rollback อัตโนมัติจากสคริปต์ smoke ที่อ่าน router metadata ไม่รองรับ FastAPI รุ่นบน server
แก้เฉพาะสคริปต์ ตรวจ candidate แบบอ่านอย่างเดียวผ่าน แล้วเผยแพร่ครั้งที่สองสำเร็จ
ได้ตรวจทั้ง rollback compatibility ในฐานแยกและการย้อน image บน UAT จริง โดยไม่คืน/ลบฐานข้อมูล
schema/evidence คงอยู่เมื่อย้อน image; ต้องพักการออก/แก้เอกสารช่วงใช้ writer รุ่นเก่าจน forward recovery
Production, runtime flags และ database containers ไม่เปลี่ยน; ยังไม่ได้ commit/push

### รายละเอียดขอบเขตระยะแรกเดิม

- เพิ่ม `/company/documents` ใน Company Shell พร้อมค้นหาและกรองหมวดเอกสาร
- แสดงเฉพาะประเภทที่ผู้ใช้มี permission เดิม ห้ามอนุมานสิทธิ์จากชื่อตำแหน่ง
- ตรวจ company และ branch context จาก server ก่อนแสดงทางเข้า
- รองรับ loading, error, empty, permission denied และ offline โดย offline เปิดรายการต้นทางไม่ได้
- ทางเข้าหน้าเจ้าหนี้ระบุแท็บผ่าน URL และรองรับย้อนกลับในเบราว์เซอร์
- ไม่สร้าง API ธุรกรรมใหม่ ไม่เพิ่มตาราง ไม่เปลี่ยนลำดับเลขเอกสาร ไม่เปลี่ยน flags และไม่ deploy
- การกรองเมนูไม่ใช่ security boundary; API ต้นทางยังต้องตรวจ scope และสิทธิ์ทุกครั้ง

## ลำดับพัฒนาต่อ

| ระยะ | ผลงาน | เงื่อนไขรับงาน |
| --- | --- | --- |
| 1 ศูนย์ทางเข้า | หน้าอ่านอย่างเดียวและลิงก์ตามสิทธิ์ | scope ตรง ไม่มี write request จากศูนย์เอกสาร เปิดแท็บถูกต้อง ใช้ desktop/tablet ได้ |
| 2 เอกสารเดิมและแม่แบบกลาง | ปรับ PO, GR และใบสำคัญจ่ายก่อน แล้วตรวจแม่แบบภาษีแยก | PDF/HTML ถูกชนิด ภาษาไทยไม่ล้น หลายหน้ามีหัวตาราง ยอดตรงต้นทาง ไม่มีการคำนวณภาษีใหม่ใน template |
| 3 ทะเบียนเอกสารและหลักฐาน | registry ฝั่ง server, snapshot, revision, audit, numbering, original/copy | ตรวจ scope ทุก query/ดาวน์โหลด เลขไม่ซ้ำเมื่อทำพร้อมกัน พิมพ์ซ้ำไม่สร้างบัญชีซ้ำ |
| 4 เอกสารขายที่ยังขาด | quotation → sales invoice → delivery → billing → receipt ตามเหตุการณ์จริง | วงจรสถานะแยกกัน รับชำระบางส่วนได้ ไม่ใช้การเปลี่ยนหัวเอกสารแทน workflow |
| 5 รายงานต่อยอด | อายุหนี้ จุดคุ้มทุน และรายรับรายจ่าย | ผู้รับผิดชอบยืนยันนิยามยอดและ cutoff ตรวจเทียบ ledger ไม่รวมบัญชีข้ามนิติบุคคล |
| 6 ตรวจรับและเผยแพร่ | ทดสอบเฉพาะส่วนเปลี่ยน ตรวจบัญชีจริงและเครื่องพิมพ์ | UAT ผ่าน อนุมัติ deployment แยกต่างหาก พร้อม rollback |

ใบลดหนี้และ invoice เดิมต้องเชื่อมเข้าระบบกลาง ไม่สร้างฐานเอกสารคู่ขนานที่ออกเลขและลงบัญชีซ้ำ
สำหรับการจ่ายระหว่างแบรนด์ในบริษัทเดียวกัน ต้องแยกจากธุรกรรมระหว่างคนละนิติบุคคล

## ข้อตกลงก่อนทำทะเบียนและแม่แบบจริง

1. แยกนิติบุคคล บริษัท แบรนด์ สาขา และฐานข้อมูลต้นทาง โดยเชื่อ context ที่ server ตรวจแล้ว
2. บันทึก snapshot ผู้ขาย ผู้ซื้อ รายการ ราคา ภาษี และยอด ณ เวลาออกเอกสาร พร้อม template version
3. ออกเลขฝั่ง server ภายใน transaction ตาม policy นิติบุคคล สาขา ปี และประเภท โดยรักษาเลขเดิม
4. เอกสารออกแล้วแก้ทับไม่ได้ ต้องใช้ revision การยกเลิก หรือเอกสารปรับปรุง พร้อมเหตุผลและผู้อนุมัติ
5. ดาวน์โหลดและพิมพ์ต้องตรวจสิทธิ์และ scope รวมทั้งไฟล์ที่จัดเก็บ ห้ามใช้ URL ถาวรแบบสาธารณะ
6. แยกใบเสนอราคา การส่งมอบ การเกิดลูกหนี้ การรับเงินจริง และ tax event ออกจากกัน
7. ไม่เปลี่ยนยอดย้อนหลังจากการแก้สูตร Excel หรือข้อมูลบริษัทปัจจุบัน

ใช้แนวทาง UX เดิมใน `docs/ux-ui/design-system/03-FORMS-DOCUMENTS-APPROVAL-PATTERNS.md`
โดยระยะแรกไม่เปิด editor, original/copy หรือ workflow ออกเอกสารที่ยังไม่มี contract

## การตรวจรับแบบไม่ทำซ้ำ

ระยะแรกใช้ type check และ browser suite เฉพาะศูนย์เอกสาร ตรวจ permission, context mismatch,
loading/error, search/empty, offline/reconnect, deep link และ desktop/tablet layout
ใช้ข้อมูล mock ในเครื่อง ไม่สร้างเอกสารหรือธุรกรรมบน UAT/Production

การตรวจ backend isolation, snapshot, numbering race, PDF หลายหน้า และการพิมพ์จริง
เป็น gate ของระยะที่เพิ่มความสามารถนั้น ไม่ถือว่าผ่านจากการมีหน้าศูนย์เอกสาร
งานที่ต้องใช้ผู้ทำบัญชีหรือเครื่องพิมพ์จริงให้คงสถานะรอตรวจ ไม่ปิด gate อัตโนมัติ

คำสั่งตรวจเฉพาะระยะแรกจากโฟลเดอร์ `frontend`:

```bash
npm run type-check
npx playwright test --config=playwright.documents.config.ts
```

ชุดทดสอบแยก local port 4196 และไม่ใช้ server ที่เปิดค้างของโครงการอื่น

## หลักฐานเอกสารระยะ 3B-AP — ขึ้น UAT แล้ว

- เก็บ `document_snapshots` เฉพาะใบสำคัญจ่ายและ WHT ที่เกิดจากการบันทึกจ่ายใหม่ พร้อมเลขเดิม ผู้จัดทำ เวลาบันทึก
  ข้อมูลบริษัท/ผู้รับเงิน รายการ ยอด และ HTML ที่ใช้ ณ เวลาบันทึก พร้อม template version และ SHA-256
- บันทึกภายใน transaction เดียวกับ payment, allocations, WHT, journal และ idempotency receipt
  ถ้าเก็บหลักฐานไม่ได้ การจ่ายและยอดค้างต้อง rollback พร้อมกัน; retry คำขอเดิมไม่สร้างหลักฐานซ้ำ
- Database trigger ป้องกัน UPDATE/DELETE/TRUNCATE จากการทำงานปกติ และ unique constraint ป้องกันหลักฐานซ้ำ
  SHA-256 เป็น checksum ตรวจความครบถ้วน ไม่ใช่ลายเซ็นดิจิทัลหรือการรับรองภาษี
- ดาวน์โหลด PDF จาก HTML ที่เก็บไว้ ไม่ดึงชื่อ/ที่อยู่คู่ค้าปัจจุบันมาแทน; ตัวไฟล์ PDF อาจต่างตาม renderer/metadata
  จึงไม่อ้างว่าเก็บ PDF byte-for-byte ถาวร
- ตรวจ company/branch/station scope เพิ่มที่ download; ไม่แก้ช่องว่าง branch isolation ของ list API เดิมทั้งหมด
- เอกสารเก่าไม่ backfill: ดาวน์โหลดตามวิธีเดิมพร้อมข้อความเตือนและ header `legacy_live_profile`
  ถ้า receipt ระบุว่าต้องมี snapshot แต่ไม่พบ ให้ปฏิเสธแทน fallback ไปข้อมูลปัจจุบัน
- รูปแบบ 50 ทวิฉบับทางการ การนำส่งภาษี และการพิมพ์จริงยังรอผู้ทำบัญชีตรวจรับ
- ทดสอบ 44 กรณี: snapshots 8, payment/WHT 26, register 10; ไม่มี frontend change จึงไม่รัน browser suite ซ้ำ
- ตรวจฐานสำเนา PostgreSQL แยกเครือข่าย: concurrent payment/idempotency, ยอดภาษี/ledger,
  เปลี่ยนบริษัท/ผู้รับเงินแล้ว PDF จาก snapshot ไม่เปลี่ยนข้อมูล, mutation guards และ atomic rollback ผ่าน
  ฐานทดสอบชั่วคราวถูกลบแล้ว ไม่สร้างธุรกรรมทดสอบบน UAT
- UAT เพิ่ม schema `docarchive0028` โดยอัปเกรดแบบระบุ revision จาก `wp65govern0026`
  ไม่รัน migration Stripe `wp84stripe0027` ที่ยังไม่ได้ deploy; merge `docmerge0029` มีเฉพาะใน checkout
  สำหรับรวมประวัติ migration ในอนาคต ไม่ได้เปิด Stripe flags
- Rollback ใช้ backend `uat-document-register-20261013` และคงตาราง/หลักฐาน/เลข revision ไว้
  ต้องพักการบันทึกจ่ายระหว่างใช้รุ่นเก่า เพราะ writer เดิมไม่สร้าง snapshot; ห้าม downgrade schema เมื่อตารางมีหลักฐาน

งานระยะ 3 ที่ยังเหลือ: snapshot PO/GR และเอกสารชนิดอื่นตามเหตุการณ์ต้นทาง,
revision/cancellation evidence, original/copy, การแสดงสถานะหลักฐานในทะเบียน และ numbering ของประเภทที่ยังไม่ครอบคลุม
ห้ามสร้าง snapshot ย้อนหลังจาก profile ปัจจุบัน; งานขายเชื่อและรายงานข้อ 4–6 ยังไม่ทำใน release นี้

### สัญญายอดเงินและการจ่าย

- ใบแจ้งหนี้ใหม่เก็บ subtotal ไม่รวม VAT และ total เท่ากับ subtotal บวก VAT ไม่หัก WHT ตอนตั้งหนี้
- การดึง PO มาเป็นใบแจ้งหนี้ใช้ยอดสุทธิ PO บวก WHT เดิมลบ VAT เป็น subtotal เพื่อไม่บวก VAT รวมราคาซ้ำ และไม่หัก WHT จาก PO ซ้ำ
- allocated_amount คือยอดตัดหนี้รวม VAT ไม่ใช่เงินโอนสุทธิ ฐาน WHT ไม่รวม VAT คำนวณบน server ด้วย Decimal
- การจ่ายบางส่วนแบ่งฐานตามสัดส่วนยอดตัดหนี้ โดยหาผลต่างฐานสะสมที่ปัดสองตำแหน่ง เพื่อรักษาฐานรวมเมื่อจ่ายครบ
- ผู้ใช้ระบุอัตรา ประเภทเงินได้หรือเหตุผลไม่หัก และยืนยันยอดก่อนบันทึก ไม่ใช้ค่า supplier 3% โดยอัตโนมัติ
- รองรับระบุฐานที่ต้องหักต่ำกว่ามูลค่าไม่รวม VAT ของงวดนั้น กรณีหลายประเภทเงินได้หรือหลายอัตราให้แยกใบแจ้งหนี้ ยังไม่ใช่ระบบจำแนกภาษีรายบรรทัด
- preview ไม่เขียนข้อมูล หน้าจ่ายแสดงยอดจาก server และตรวจอีกครั้งตอนบันทึก ปฏิเสธยอด WHT จาก client ที่ไม่ตรงกัน
- เงินจ่ายสุทธิเท่ากับยอดตัดหนี้ลบ WHT; เครดิตบัญชี WHT และใบรับรองใช้ยอดเดียวกัน ใบรับรองบันทึกฐานไม่รวม VAT ณ ครั้งจ่าย
- ไม่ตัดยอดค้าง 0.01 บาททิ้ง ใบเก่าที่ wht_amount มากกว่า 0 ถูกระงับการจ่ายต่อเพื่อให้บัญชีตรวจทาน ไม่แก้บัญชีหรือใบรับรองเก่าย้อนหลัง

หลักการหักภาษีเมื่อจ่ายอ้างอิง [กรมสรรพากร](https://www.rd.go.th/27862.html)
ตัวอย่างการใช้ฐานไม่รวม VAT มีใน [ข้อหารือ กค 0706/40](https://www.rd.go.th/24856.html)
อัตราเฉพาะในข้อหารือนั้นไม่ใช่อัตราเริ่มต้นของระบบ ต้องพิจารณาประเภทเงินได้และผู้รับเงินของแต่ละรายการ

### ความปลอดภัยของธุรกรรม

- ตรวจบริษัทและสาขาของใบแจ้งหนี้ ผู้จำหน่ายเดียวกัน วันจ่ายไม่ก่อนใบแจ้งหนี้ และล็อกใบแจ้งหนี้ขณะตัดยอด
- ใช้ idempotency_key และลายนิ้วมือคำขอ เก็บ receipt ใน AuditLog พร้อมการจ่ายใน transaction เดียวกัน คำขอเดิมคืนผลเดิม ข้อมูลต่างกันแต่ใช้รหัสเดิมถูกปฏิเสธ
- ห้ามลบ audit action `accounting.payment.request` ก่อนสิ้นอายุเก็บรายการจ่าย เพราะเป็นหลักฐานป้องกันจ่ายซ้ำ ปุ่มตรวจผลคำขอเดิมใช้ payload เดิมเมื่อผลเครือข่ายไม่แน่นอน
- เลข SINV PAY WHT ใช้ advisory lock ที่คงที่ข้าม worker และลำดับไม่ชนข้ามบริษัทตาม unique constraint เดิม เลขเก่าไม่เปลี่ยน
- การยกเลิกใบแจ้งหนี้ล็อกแถวและกลับรายการบัญชีใน transaction เดียวกัน ไม่เปิดช่อง commit ระหว่างทาง
- ไม่มี schema migration; frontend และ backend ต้องเผยแพร่พร้อมกัน เพราะ API จ่ายใหม่ต้องมี idempotency_key และ wht_reviewed

### ผลตรวจและเงื่อนไขก่อนเผยแพร่

- Backend regression เฉพาะเจ้าหนี้ 25 กรณีผ่าน และแม่แบบเอกสารเดิม 15 กรณีผ่าน
- Type check ผ่าน และ browser mock 3 กรณีผ่าน ครอบคลุม desktop/tablet การจ่ายบางส่วน ใบเก่าที่หักแล้ว และ retry payload เดิม
- ทดสอบ service ด้วย session จำลองและตรวจ SQL lock ไม่ใช่การทดสอบ race บน PostgreSQL จริง ยังต้องตรวจ integration กับฐาน UAT ก่อนปิด gate
- รูปแบบ 50 ทวิฉบับทางการ การพิมพ์จริง ภาษีที่ผู้จ่ายออกให้ การนำส่งภาษี และ immutable snapshot ผู้จ่าย/ผู้รับ ยังไม่ถือว่ารับรองจากงานชุดนี้
- แม่แบบและข้อมูลเอกสารเก่าไม่ถูกคำนวณใหม่ งานนี้ไม่เปิด Production flags
